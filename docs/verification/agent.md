# Verification guide: apps/agent

`apps/agent` is one Cloudflare Worker: the Edge, the Personal Agent Durable Object, and the Directory D1 binding. Terms follow [CONTEXT.md](../../CONTEXT.md).

## Message flow

1. Telegram sends an update to `POST /telegram/webhook`. The Edge checks the `X-Telegram-Bot-Api-Secret-Token` header and keeps only text messages and Approval button presses (`callback_query` with `approve:<id>` or `reject:<id>`) from private chats. The webhook setup (`setWebhook`) sets `allowed_updates` to `["message", "callback_query"]`, so Telegram sends the presses.
2. The Edge finds the Owner for the Channel Identity `telegram:<user id>` through the Directory. It reads with a D1 session from the nearest replica. When the replica has no row, it reads the primary, so an Owner who was just added is not lost to replica lag.
3. The Edge gives the Event to the Owner's Personal Agent. The Personal Agent stores the Event in its Inbox and writes an `EventReceived` Journal Entry. For an Owner message, it arms its durable alarm (the Agents SDK `schedule`) for when the pending Owner messages are due as a Burst: `burstQuietMillis` (2.5 seconds) after the newest, or `burstMaxWaitMillis` (10 seconds) after the first, whichever comes first, and the Schedules store keeps the alarm at the earlier of that instant and the next Schedule (decision 0022). When the alarm cannot be armed, the Personal Agent fails the Event's hand-off, so the Edge answers with an error and Telegram retries; the retry is a duplicate, so the Event is not stored again, and it arms the alarm (`fails the rearm that an arriving Owner message needs when the alarm cannot be set` in `test/schedules.test.ts`). While the Burst waits, each message shows the typing signal once. Then the Edge answers 200.
4. The alarm runs one Turn. For an Owner message, the Turn first shows the typing signal (Acknowledge): Telegram `sendChatAction` with `typing`, sent at once and again every `typingRepeatMillis` on a fixed cadence (an attempt with no answer within one interval is given up, so the next one still goes) (4 seconds in the Behavior Config, because Telegram shows it for about 5 seconds), until the outcome of that Event starts to send or the Turn restarts: the Channel send of the reply, or of the honest failure notice, stops typing first, so no signal follows the outcome. Typing is best-effort: a failed or unanswered `sendChatAction` is logged and never fails or delays the Turn, and it is not a Delivery. A Reminder, a Scheduled Task, and a Proactive Message show no typing. The Turn answers the pending Owner messages that are due as one Burst first, in arrival order, with one outcome in reply to the newest message, and then the other Events, oldest first. For each Burst or Event, it reads the whole stored Conversation and asks the Model Gateway for a reply with the request layout of decision 0033: the fixed system prompt of the Turn kind, the Owner Context Block (the time zone and the Profile), the Conversation, then the new input, which starts with the Turn Context Block (the current local time of the Owner, or that the time zone is not known, and the situation of the Turn, up to `[End of Turn context]`). The Model Gateway runs the AI SDK `ToolLoopAgent` (built for each request, so per-step hooks, MCP tools, and `toolApproval` can join its settings) with the tools of the Turn and the step limit of the Behavior Config (`maxToolSteps`), and records Usage for every step. Only a model call is retried and has a timeout. A tool runs once, through the Effect runtime of the Personal Agent, and a tool failure reaches the model as an error result. When the loop ends on a tool call at the step limit, the Turn fails and sends the honest failure message. A failed Turn still keeps the tool calls and results of its finished steps in `Conversation`, so the next Turn knows what its tools did. `Conversation` stores AI SDK `ModelMessage` values (JSON, checked by a schema), including tool calls and tool results, and each row has its Turn Event id and a row kind (`input`, `step`, `reply`, or `approval_status`). The history has no window: every stored row is sent (`test/tool-loop.test.ts`). The versioned migration `20261124202916_conversation_layout` deletes the stored rows of the earlier layout. Request layout (`test/request-layout.test.ts`), through the Durable Object with the scripted model: two Owner message Turns in a row, the first with a `capture_note` step, send a byte-identical system message, tool definitions, and message prefix up to the end of the first Turn as it is stored; the system message is the same bytes for two Owners and two Turns and has no time, time zone, Profile, or situation; a Profile change replaces the Owner Context Block one time while the system message and the tool definitions stay the same bytes; the stored rows of a Turn are the Owner message with its Turn Context Block at the start, as it was sent, and the reply, with one Turn Event id; recovery after a reset stores the Owner message with the Turn Context Block that the Turn sent (`test/stored-turn.test.ts`); and after a Turn is done, no `turn_progress` or `turn_context_blocks` row of it is left.
5. The Turn writes `ReplyPlanned` and `SendStarted`, then sends the reply with Telegram `sendMessage`. A reply longer than 4,096 characters goes as several messages, cut at a line break or a space when possible, and the send is confirmed only when Telegram confirms every part. It writes `ReplySent` only with the Telegram message id. A refused or failed send writes `ReplyFailed` and then `TurnFailed` with the same reason, and the Events are failed.
6. When the model fails 3 times, the Turn writes `TurnFailed` with the reason, then sends one honest message through the same `ReplyPlanned`, `SendStarted`, and `ReplySent` or `ReplyFailed` steps, and fails the Event. 6a. After the model call, and before it delivers anything, an Owner message Turn checks the Inbox for a pending Owner message that arrived after the newest message of its Burst and has no Turn of its own (decision [0025](../decisions/0025-restart-mid-turn.md), Option A). When there is one, fewer than `burstMaxRestarts` (2) restarts were written for the Turn Event, and `burstMaxWaitMillis` has not passed since the first message, the Turn sends nothing and writes no `ReplyPlanned`, `StayedSilent`, or `TurnFailed`. In one transaction it writes the restart record and a Trace with the `restart` field. The record is stored as an `EventReceived` Entry for the Turn Event with a `restart` field (the covered and the new Event ids), so an earlier version still reads it. Then it writes a `superseded` Operator metric, and leaves the Events pending. The next Turn starts after the Quiet Gap with every message of the Burst, and the tool calls that already finished come back from Turn progress as completed steps, so no write tool runs again.
7. After the model call, and before `ReplyPlanned` or `TurnFailed`, the Turn writes one Trace. So a Journal with `ReplyPlanned` or `TurnFailed` for an Event always has a Trace for it. A Turn that runs again after a crash or a restart writes a new Trace, and the earlier one stays.
8. At the end of the Turn, and for each refused request at the Edge, the Worker writes one Analytics Engine data point.
9. The Schedules store keeps one Agents SDK alarm (callback `fireDueSchedules`) at the earliest due instant of its active Schedules, and arms it again after each change and after the due Events are stored and the Turn is queued (`describe("Schedules store alarm")` in `test/schedules.test.ts` checks set, change, cancel, a time zone change, and that the alarm stays until the hand-off is done). When it runs, each due Schedule enters the Inbox as a `ScheduleFired` Event (one for each Schedule id and due instant), and a Turn is scheduled. A `RunPrompt` Schedule is a Scheduled Task. Its Turn runs the Model Task `scheduled_task` with read tools only, as decision [0015](../decisions/0015-scheduled-task-turn.md) says. For a `ScheduleFired` Event of a `SendText` Schedule the Turn makes no model call. It sends the saved Reminder text to the Owner Channel Conversation through the same `ReplyPlanned`, `SendStarted`, and `ReplySent` or `ReplyFailed` steps, marks a one-time Schedule `done` only after a confirmed send (a repeating Schedule stays `active` and gets its next due instant, see the repeating Reminders entry), writes one Trace with the result `reminder_delivered` or `reminder_delivery_failed`, and writes one Operator metric of the kind `reminder`.

## Traces and Operator metrics

A Trace is a row of `turn_traces` in the Personal Agent SQLite. The row has the Owner Id, the Event id, the result (`model_replied` or `model_failed` for a model-answered Event; `reminder_delivered` or `reminder_delivery_failed` for a Reminder, whose record has the Schedule id, the due instant, the text, and no model fields), and a JSON record with the task, the model id, the model settings (attempts and timeout of each attempt), the request pointer, the steps (the tool calls of each step with their call id, input, output, and failure flag, and the Usage of each step), the reply or the error, the summed Usage, and the model latency. The Trace redacts every step. A Scheduled Task Turn has the result `scheduled_task_replied` or `scheduled_task_failed`. Its record adds the Schedule id and the due instant to the model fields. A skipped Scheduled Task has the result `scheduled_task_skipped`. Its record has the Schedule id, the due instant, the Budget, the spent tokens, and the message, and no model fields. A Turn that reaches the step limit has a `model_failed` Trace with its steps. Operator metrics carry the number of steps and tool calls and no content. The request pointer (decision 0034) holds no copy of the request prefix: it has a SHA-256 hash of the system text, of the serialized tool definitions (type, name, description, and input JSON Schema of each tool, in the order sent), and of the Owner Context Block, the range of the Conversation rows that the request sent (the Summary row sequence and the first and last sequence of the other rows; all null for a Side Session and for an empty history) with a hash of those rows as sent, and in full only the tail: the Turn Context Block or Run block with the new input, and the steps of an earlier attempt of the Turn, with a hash of the tail as sent. Each version of the system text, the tool definitions, and the Owner Context Block is stored once under its kind, its Turn kind (`reply`, `scheduled_task`, or `proactive`), and its hash in `trace_request_parts`, with the time of its last use, in the same transaction as the Trace. `trace_request_part_uses` links each Trace to the three versions that it uses, and a delete of the Trace deletes its links (a foreign key with `ON DELETE CASCADE`). `replayTurn` (`src/tracing/trace-replay.ts`) builds the exact request from the stored versions and the Conversation rows of the range, also compacted ones, and checks each part against its hash. A part that is missing or changed is reported (`PartsDiffer` with the part and `missing` or `changed`) and is never replaced by the current one. A Conversation row that no longer decodes is a changed part, and a tail that the Redactor changed is a changed `tail`. A Trace recorded before decision 0034 has its copied prompt under `request` with the kind `copy`, and replay returns it as `RecordedInFull`. The stored versions are redacted; a version that held a secret fails its hash check. The table refuses every update with a storage trigger, and refuses a delete of a Trace that is newer than the fixed floor of 7 days. The interface has only record, read, and replay.

Retention (decision 0034): `traceRetentionDays` of the Behavior Config (first value 30, a branded Schema that refuses a value below the floor of 7 or above the ceiling of 36,500, so the date arithmetic stays valid) sets the period. The `fireDueSchedules` alarm runs the retention step at most once a day (`trace_retention_runs` holds the last run), with no model call. In one transaction it deletes each Trace recorded at least that period ago, each Conversation row compacted at least that period ago (the clock starts at the Compaction, not at the creation of the row), and each stored version that is not the last used one of its kind and Turn kind and that no Trace uses (no row of `trace_request_part_uses`). The Journal is never deleted. The Schedules store arms the alarm also at the instant when the oldest Trace or compacted row expires, and not earlier than one day after the last run and, after a failed run, not earlier than one minute after the failure (the Personal Agent keeps that instant in memory and clears it after a run that succeeds). Until that instant, an alarm for another reason skips only the retention step and still handles the Pending Approvals and Schedules. So a failed run gets a new alarm one minute later and never a past one, which could match the running alarm and arm nothing. Without a failure, an overdue run keeps its past due instant, so a rearm that runs no retention (for example at the end of an ApprovalAnswered Turn) arms an alarm that fires at once and does not move the run. A test rearms twice with an overdue Trace, checks that the alarm stays at the due instant, and runs the alarm, which deletes the Trace. The test Worker sets `traceRetentionDays` to 3,650 (`fakeTraceRetention`), so the retention alarm comes after the fixed due instants of the Schedule tests. A test that expects no Schedule alarm expects only the retention alarm (`test/trace-retention-alarm.ts`). The retention tests set 30. The Trace records the model call only. The send result of the same Event is in the Journal (`ReplySent` or `ReplyFailed`), found by the Event id, so a Turn whose send failed has a `model_replied` Trace and a `ReplyFailed` Journal Entry. The Trace has private content and never leaves the Personal Agent.

The Operator metrics go to the Analytics Engine dataset `assistant_operator_metrics` (binding `OPERATOR_METRICS`). Each data point has:

| Field | Value |
| --- | --- |
| `index1` | The Owner Id, or `none` when the request has no Owner |
| `blob1` | `turn`, `reminder`, `scheduled_task_skipped`, `proactive_message`, `outcome`, or `refused` |
| `blob2` | The result: `replied`, `reacted`, `silent`, `model_failed`, `send_failed`, or `superseded` (an answer that a restart dropped) for a Turn; `sent` for a Proactive Message; `acted`, `replied`, `muted`, or `ignored` for an Outcome; `bad_secret_token`, `unknown_sender`, or `owner_not_active` for a refused request |
| `blob3` | The model id for a Turn, empty for a refused request |
| `blob4` | `cost_known` or `cost_unknown` for a Turn, empty for a refused request |
| `blob5` | The Event id of the Turn, Reminder, skipped Scheduled Task, or Proactive Message (for an Outcome, the Event id of the Proactive Message). Empty for a refused request, because no Event exists yet. |
| `double1` | Latency in milliseconds. For a Turn: from the start of the Turn for the Event to the end of the send. For an Outcome: the time from the send of the Proactive Message to the Outcome. For a refused request: the time in the Edge. |
| `double2` to `double5` | Input tokens, output tokens, cost in USD, cached input tokens. The value is 0 when the provider gave none. |
| `double6` to `double8` | For a Turn: the number of steps, the number of tool calls, and the restart count of the Turn Event (the number of `EventReceived` Journal Entries of the Turn Event that carry a `restart` field; for a `superseded` data point it includes that restart). The value is 0 for other kinds. |

A model step data point (`blob1` is `model_step`) is written for each model step of a reply Turn, a Scheduled Task Turn, a Proactive Turn, and a Compaction, right after the model call and before the Delivery (decision 0033). It is the source of the Hit Rate. Its fields are different:

| Field | Value |
| --- | --- |
| `index1` | The Owner Id |
| `blob2` | The planned-miss reason that code knows for step 1 of the run, or `none`. The reasons are `no_earlier_call` (the session has no earlier call), `cache_lifetime` (more than 60 minutes since the earlier call), `deploy` (the system text or a tool definition of the Turn kind changed), `owner_context_changed`, `compaction` (the first main Conversation call after a Compaction), and `stub_in_turn_before` (the main Conversation Turn before was stored with a Stub). Step 2 and later is always `none`. A Forget is a planned miss of decision 0033 that comes with #138. |
| `blob3`, `blob4`, `blob5` | The model id, `cost_known` or `cost_unknown`, and the Event id of the Turn |
| `blob6` | The session: the Model Task `reply`, `scheduled_task`, or `proactive` (the Turn kind), or `compaction`. The main Conversation is `reply`, each Side Session kind is its own session, and Compaction is a session of its own. The Hit Rate of `doctor` counts only the three Turn kinds, because a Compaction sends its block as data and not as the stored prefix. |
| `double2` to `double5` | Input tokens, output tokens, cost in USD, and cached input tokens of the step |
| `double6` | The step number in the Turn: 1 is the cross-Turn call, 2 and later are in the Turn. A run after a reset or a Restart continues the count. |
| `double9` | The minutes from the start of the earlier model call of that session to the start of this call, or -1 when the session has no earlier call |

The Personal Agent keeps one row for each session in `prefix_cache_sessions`: the start time of its last model call and the SHA-256 of its system text, its serialized tool definitions, and its Owner Context Block. A Compaction and a stored main Conversation Turn with a Stub mark the `reply` row in the same transaction as the Conversation write, and the next call of the session reads and clears the mark.

A reset can repeat a data point, and a repeat carries the same Event id. For a skipped Scheduled Task, recovery also writes a missing data point, so a reset does not lose it. For the event-level kinds (all kinds except `model_step`), readers must count distinct Event ids in `blob5`, never rows. A Turn that restarts writes one `superseded` data point for each dropped answer, with the Event id of the Turn Event, and one data point for the final outcome with the same Event id, so count restarts with `double8` of the final data point. A `model_step` data point is one model step, so a Turn with two steps writes two of them with the same Event id. Readers sum `model_step` rows (weighted by `_sample_interval`) and group them by the step number in `double6`, as `doctor` does. After a reset, the Turn calls the model again, and each new call writes its own data point. The Analytics Engine allows 20 blobs, 20 doubles, and one index of 96 bytes. The Event id is a new last blob, so `blob1` to `blob4` keep their positions. The index stays the Owner Id, because it is the sampling key.

The metric type allows only these fields, so message content cannot enter a data point. The cost is always 0 and `blob4` is `cost_unknown` now, because the AI SDK does not report the cost. Reading the cost from AI Gateway is a known gap. A data point is written after the send, so a Turn that stops between a confirmed send and the data point has none. The data points are best-effort; the Journal and the Trace are the record. A write that throws is logged as a warning without content and never stops the Edge response or the Turn.

Secrets: the Redactor replaces the values of `TELEGRAM_BOT_TOKEN`, `AI_GATEWAY_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, and `OPERATOR_TOKEN` in the model error, in the Telegram failure reason, in the reply, and in the tail and the stored request versions of the Trace, before they enter a Trace or the Journal. The Inbox keeps the Owner message as sent.

AI Gateway keeps no prompt or reply text because each request sends `cf-aig-collect-log-payload: false`. A test checks the header. The gateway-level logging setting in the Cloudflare account is not checked here. Check it on the deployed account (it needs the repository owner's approval) and record the result in the PR.

The Operator adds the Owner with `POST /operator/owners`. This route needs `Authorization: Bearer <OPERATOR_TOKEN>` and writes through the Directory interface. It does not open Registration.

## Verify a change

Run `pnpm verify` at the repository root. Turborepo runs the `verify` script of each workspace that the branch changed (`turbo run verify --affected`). To run only this workspace, run `pnpm --filter @repo/agent verify`.

The workspace `verify` script runs these checks in this order:

| Command | What it proves |
| --- | --- |
| `pnpm typecheck` | `worker-configuration.d.ts` matches `wrangler.jsonc` (`wrangler types --check`). The Worker code, the tests, and the control CLI type-check. |
| `pnpm control map --check` | The [Feature Map](agent-feature-map.md) matches the Edge route table in `src/edge/routes.ts`. |
| `pnpm test` | The behavior tests pass (see below). |
| `pnpm control bundle` | The Worker builds with a dry run and is below the Workers size limit. |

After a change to a table schema, run `pnpm --filter @repo/agent migrations:generate` and commit the new migration files.

After a change to `wrangler.jsonc`, run `pnpm --filter @repo/agent types` and commit the new `worker-configuration.d.ts`.

The root lint rules let only `src/personal-agent` and the MCP Hub (`src/mcp/mcp-hub.ts` and its manager subclass) import the Agents SDK (decision 0003 and 0036). Other modules use `personalAgentFor` and the `PersonalAgent` class.

## Behavior tests

Vitest runs two projects.

- `worker`: tests in `test/` run inside workerd with `@cloudflare/vitest-plugin`. They use real Durable Objects with SQLite storage and a real local D1 database. Each test file gets isolated storage.
- `control`: tests in `control/` run in Node and check the control CLI. The Eval tests start the eval Worker in the wrangler test harness with the local fakes (see [Eval](#eval)).

Local fixtures:

- Test Worker entry. `test/worker.ts` exports the real Edge and a `PersonalAgent` subclass. The subclass gives the Turn a fake model from the AI SDK test utilities (`MockLanguageModelV4`) and the real Telegram Channel with a fake Telegram API `fetch`. A fake Analytics Engine dataset replaces the `OPERATOR_METRICS` binding for the Edge and the Turn. The fakes are in `test/fakes.ts`, and they record each call. The real Model Gateway, Inbox, Journal, and Usage code runs.
- Directory migrations. `test/apply-migrations.ts` applies `src/directory/migrations/*/migration.sql` to the test D1 database before each test file.
- Personal Agent migrations. Each Personal Agent applies `src/personal-agent/migrations` when it builds its storage layer. Drizzle Kit generates both sets from the table schemas (decision 0007).
- No network. The test runtime answers every outbound `fetch` with status 503 and the text `Network is off in tests: <url>`. Remote bindings are off. A test proves this.
- Test secrets. `vitest.config.mts` sets fixed fake values for the required secrets. Tests never read `.dev.vars`.
- Loading the Agents SDK module graph is slow in the test runtime. The `worker` project pre-bundles `agents`, `effect`, `drizzle-orm`, and the Effect SQL clients with the Vitest dependency optimizer. Without the Drizzle and SQL entries, the module graph is too large for the test worker connection and the run fails with `Message is too large`. Tests import Worker modules at the top of the file, so the load happens while Vitest collects the file, not inside a test with a time limit. Call the Worker as `worker.fetch(request, env, createExecutionContext())`. Do not use `exports.default.fetch` in tests: its first call loads the module graph inside the test and can time out on a cold run.

What the tests prove now:

- The Operator route adds the Owner and the Channel Identity through the Directory, and Registration stays closed. A request without the Operator token gets 401 and stores nothing. A Channel Identity that already has an Owner gets 409.
- A webhook request with a missing or wrong secret token (also one of another length) gets 401. The Owner's Personal Agent has no Inbox Event and no Journal Entry, and the fake Telegram API gets no `sendMessage`.
- A text message from an unknown sender, or from an Owner who is suspended, gets 200 and no reply. The Directory gains no Owner and no Channel Identity, and the Owner's Personal Agent keeps no content.
- A sticker, an edited message, a group chat text, a text from a bot, and a body that is not an update (or not JSON) get 200 and are ignored. The Owner's Personal Agent keeps no Event and no Journal Entry, and no reply is sent. Only a wrong or missing secret token gets 401. Telegram always sends the correct token, so it does not retry; the refusal reaches only other callers.
- A text message from the Owner is in the Inbox when the webhook answers 200, while the fake model still holds the Turn. The alarm then runs the Turn, and the fake Telegram API gets exactly one `sendMessage`: plain text, to the Owner's chat, as a reply to the Owner's message.
- The prompt has the static system part first, then the conversation, then the new message.
- Each Turn with a successful model call and a confirmed send writes `EventReceived`, `ReplyPlanned`, `SendStarted`, and `ReplySent` Journal Entries for the Owner, and one Usage row with input, output, and cached tokens. A Turn whose model failed 3 times writes no Usage row.
- A model that fails 3 times gives a `TurnFailed` entry with the reason and exactly one honest `sendMessage`. A Turn that stopped after `TurnFailed` sends the honest message once, does not call the model again, and keeps the Event failed, also when the honest message was already confirmed. When the honest message started to send without a confirmation, the Turn writes `ReplyFailed` and does not send again. An honest message that Telegram refuses is recorded as `ReplyFailed`, never as sent, and is not sent again.
- A send that Telegram refuses writes `ReplyFailed` and never `ReplySent`.
- An update that Telegram sends again (same `update_id`), also after the Turn finished, gets 200 and no second Event and no second `sendMessage`.
- An Event whose Turn stopped before the reply was planned gets one reply when the Turn runs again. An Event with a confirmed send in the Journal gets no second `sendMessage` and is marked done, unless the Journal has `TurnFailed`; then the Event stays failed.
- A `ReplyPlanned` entry without `SendStarted` means that no message left yet, so the Turn plans and sends again. When a send started (`SendStarted`) but the Journal has no confirmation, the Turn does not send again. It writes `ReplyFailed` with the reason that the send was not confirmed and marks the Event failed. A test with a Telegram answer that is lost in transit shows one `sendMessage` and no second one. Reason: Telegram cannot tell the agent whether a message arrived, so the rule never sends a second time and accepts that the Owner may get no reply. The Owner can send the message again.
- A webhook for an update that is already stored schedules a Turn while any Event is pending, so a crash between storing and scheduling heals when Telegram sends the update again. The recovery tests start the Turn from the Agents SDK alarm (`schedule`), not by a direct call. One test resets the Durable Object while the fake model holds a Turn, runs the saved alarm again, and finds one `sendMessage`.
- A reply longer than the Telegram limit of 4,096 characters is split into parts within the limit, without a cut inside an emoji. It is confirmed only when every part is confirmed, and a failed part fails the delivery.
- A Personal Agent on an older schema keeps its rows when a later migration changes a table, and applies each migration once. A migration that fails leaves no partial schema and fails the storage layer with `MigrationFailed`.
- The Journal storage refuses updates and deletes, and entries stay the same after a later Turn.
- The Model Gateway calls `<AI Gateway URL>/chat/completions` with `cf-aig-gateway-id`, the Owner Id in `cf-aig-metadata`, `cf-aig-collect-log-payload: false`, `cf-aig-skip-cache: true`, and `x-session-affinity` (the SHA-256 of a fixed prefix and the Owner Id). The session affinity value is the same for two Turns of one Owner and for the main Conversation and the Side Sessions, different for two Owners, and it is not the Owner Id (`test/model-gateway.test.ts`).
- Hit Rate metric (`test/prefix-cache-metric.test.ts`, decision [0033](../decisions/0033-prompt-and-conversation-architecture.md)): a Turn with a tool call writes one `model_step` data point for each model step, with the Turn kind, the step number, the tokens, the minutes since the earlier call, and no text of the Owner or the reply. The first call of a session records `no_earlier_call`, and step 1 of the next Turn inside the cache lifetime records `none`. Step 1 after a Profile change records `owner_context_changed`, after an `untrusted` Turn `stub_in_turn_before` (and the Turn after that `none`), and after a Compaction `compaction`; the Compaction call itself writes a data point with the session `compaction`. Unit tests of `plannedMissOf` cover `cache_lifetime` and `deploy`.
- Each Turn writes one Trace with the request pointer, the model settings, the reply, and Usage. Replay of the Trace of an Owner message Turn, of a Turn after a Compaction, and of a Side Session gives a request whose prompt and tools are byte-identical to the call that the fake model recorded (`test/trace-replay.test.ts` sends the replayed request to the fake model again). After a change of a tool definition, replay uses the stored version. A deleted system version, a changed tool definitions version, a changed Conversation row, a row that no longer decodes, and a tail with a redacted secret are each reported. The Trace of an Owner message Turn holds no earlier Owner message, no Owner Context Block, and no system text, and the Trace after a Compaction holds no Summary. A Turn whose model failed 3 times writes a `model_failed` Trace with the error. A secret in the model error, in the Owner message, or in the reply is replaced and appears in no Trace, no Journal Entry, and no Usage row. The Trace storage refuses every update and a delete of a Trace newer than the floor of 7 days, and allows a delete of an older one. On the alarm, the retention step deletes a Trace recorded 31 days ago and a row compacted 31 days ago, keeps a Trace recorded 29 days ago, keeps a row created 45 days ago that was compacted 2 days ago (and the Trace that points to it replays), deletes a stored version that is not current and that no Trace points to, keeps the current one, and changes no Journal Entry. After a Turn, the alarm is armed at the instant when its Trace expires. A retention value below the floor is refused. The migration moves the copied prompt of an earlier Trace into `request` with the kind `copy` and keeps the update trigger (`test/trace-retention-migration.test.ts`).
- Each Turn writes one Analytics Engine data point with the Owner Id, the result, latency, tokens, and cache hits. A refused request (missing or wrong secret token, unknown sender, or an Owner who is not active) writes one data point with the reason. A non-text update writes none. No data point holds message text. A throwing dataset changes no Edge status and does not stop the Turn.
- Event union (`test/schedule-fired-event.test.ts`, `test/telegram-channel.test.ts`): the Inbox keeps one `ScheduleFired` Event when it stores the same Schedule id and due instant twice. - A `change` call that the model makes from that result waits for Approval (the Turn is `untrusted`) and runs nothing; Approve on it runs it through the tools of the first Owner Turn and gives a third message.
- A failed call gives the model the error "The approved call failed: The service reported an error ...", and a timeout gives the unconfirmed text; neither result says done.
- The Turn refuses `stay_silent` and sends a text, with no reaction.
- Two Approve presses at the same time give two ordered messages, one for each call.
- An abort after the run and before the answer gives one answer message after the alarm, and the call runs once.

Known limit: the scripted model writes the answer text, so the tests prove what the model gets and that a new message is sent, not the words that a real model writes.

## Eval

`pnpm control eval --k <n> [--case <name>]...` measures the agent with the real model (decisions [0011](../decisions/0011-eval-runner.md) and [0012](../decisions/0012-eval-owners-and-judge-evidence.md)). It costs money. It is not part of `pnpm verify`, and an agent runs it only with the repository owner's approval (decision 0037). Set `AI_GATEWAY_URL` and `AI_GATEWAY_TOKEN` in the environment or in `.dev.vars`.

1. It loads every case in `control/eval/cases` (or only the `--case` names) and decodes it with the case schema. An invalid file stops the command with the file name and the path of the bad field, before any model call.
2. It prints the range of expected model calls: for each run, 1 to `maxToolSteps` model steps for each Owner Event, and 1 judge call for each `reply_judged` check. Each call can have up to 3 attempts.
3. It starts the eval Worker (`eval/worker.ts`) in the wrangler test harness with temporary storage, random local secrets, a fake Telegram API on `127.0.0.1`, and the real AI Gateway. The eval Worker is the real Edge and Personal Agent plus the `/eval/seed`, `/eval/observation`, and `/eval/judge` routes, which need the local Operator token. The deployed Worker does not include them. The agent and the Judge use the routes of `MODEL_ROUTES` in `wrangler.jsonc`, the same table as the deployed Instance.
4. For each run, it adds a new Owner through the Operator route, seeds the case Notes and Profile entries, sends each Owner Event to the webhook, and waits until the Inbox has no pending Event. Then it reads the Notes with links, the Profile, the tool calls in the Traces, and the Usage, and applies the checks.
5. The report lists each case with PASS or FAIL, the passed runs of k, each failed check with its run and what the runner found, the agent and judge tokens, and the cost (unknown until #27). The command exits with 1 when a case fails.

A case file exports a default object that `satisfies EvalCaseFile`. Its name is the file name. Fields:

- `description`: what the case measures.
- `seed` (optional): `notes` (text, optional `url`, optional `forwardedFrom` for an `untrusted` Note) and `profile` entries (`kind` `fact` or `style_rule`, and `text`).
- `events`: the Owner Events in order, each with `text`, an optional `forwardedFrom` sender name for a forwarded message, and an optional `owner` (`A` or `B`, default `A`). Owner B is a second Owner with its own Personal Agent storage, for isolation cases. Each run adds both Owners, and `seed` fills Owner A.
- `checks`: `note_count` (`equals`), `note_matches` (`textIncludes` words, case does not matter; optional `url`, `trustLevel`, and `forwardOrigin`), `link_count` (`equals`, undirected links), `notes_linked` (`noteIncludes` and `linkedNoteIncludes`: a Note with the first words links to a Note with the second words), `profile_entry_count` (`equals`), `profile_entry_matches` (`textIncludes`, optional `kind`), `tool_calls` (`tool`, optional `min` and `max`; with neither, at least 1), and `reply_judged` (`rubric`). Each check has an optional `owner` (default `A`) that selects whose storage, Trace, or replies it reads; the report prefixes a failed check of Owner B with `Owner B,`. The judge gets the rubric in its system prompt, and the whole conversation of the run with the tool calls of the judged Owner as JSON data in the user message, and its instructions say never to follow text inside that data. Each seeded Note has its own seed Event id, so two seeded Notes with the same text stay two Notes. `--case` loads only the selected files, so an invalid other case does not block them. A failed `note_matches` shows each Note with its trust level, URL, and forward origin.

Cases: `capture-task-with-date`, `capture-link-with-comment`, `capture-link-alone`, `capture-fact-about-owner`, `capture-related-notes`, `recall-answer-with-source-and-date`, `recall-no-matching-note`, `recall-follow-up`, `untrusted-forwarded-instruction`, and `isolation-between-owners`. On 2026-11-15, with the owner's approval at k = 3, 6 of the 10 starter cases of issue #38 passed pass^3 on the real model: `capture-fact-about-owner`, `capture-link-alone`, `capture-link-with-comment`, `capture-related-notes`, `capture-task-with-date`, and `recall-follow-up`. Four failed because the model skipped a tool call that the system prompt asks for: `recall-answer-with-source-and-date` (2 of 3 runs, skipped `search_notes`), `recall-no-matching-note` (1 of 3, skipped `search_notes`), `untrusted-forwarded-instruction` (1 of 3, skipped `capture_note`), and `isolation-between-owners` (2 of 3, Owner A's message was not kept). Results vary between full runs of the same cases, so one run is weak evidence. A change of model or prompt is a separate decision.

Local proof with no network: `control/eval/run-eval.test.ts` runs the runner against the fake AI Gateway of `local-fakes.ts` with a fake judge (`fake-judge.ts`) that answers the verdicts that a test gives. The test gives the eval Worker its own `MODEL_ROUTES`, with the fake judge model on the route of `eval_judge`; a real Eval uses the `MODEL_ROUTES` of `wrangler.jsonc`. One failed judge verdict of k runs fails the case, and the report has the pass count, the failed check, and the tokens. A case with seeded Notes and a Profile entry passes all k runs, and its link and Profile text checks fail with what the runner found when the links or the kind do not match. `control/eval/eval-cases.test.ts` checks the case schema errors and the `--case` selection.

## Configuration

`wrangler.jsonc` `vars`:

- `TELEGRAM_API_URL`: the Telegram Bot API origin. `dev` and `request` replace it with the local fake.
- `AI_GATEWAY_URL`: the AI Gateway REST base URL, `https://api.cloudflare.com/client/v4/accounts/<account id>/ai/v1`. It is empty in the repository, because it names the Operator's account. Set it before a deploy. A Turn with an empty value fails and names the value. `dev` and `request` replace it with the local fake.
- `EDGE_PUBLIC_URL`: the public HTTPS origin of the Edge, for example `https://agent.example.workers.dev`, with no trailing slash. The Telegram Channel builds the `login_url` of the Connect button from it. Set the same domain in BotFather with `/setdomain` for the bot (see [Set up MCP Connections](#set-up-mcp-connections)). Empty means that no Connect button can be sent.
- `AI_GATEWAY_ID`: the gateway that the request names in `cf-aig-gateway-id`.
- `MODEL_ROUTES`: the route table of the Model Gateway (decision [0034](../decisions/0034-architecture-review-changes.md)), one JSON object and the only model configuration:
  - `primary`, `secondary`, and `reviewer`: three routes. A route is a `model` and a `reasoningEffort`.
  - `model`: the name that the AI Gateway REST endpoint uses. A Workers AI model has the `@cf/` name, for example `@cf/deepseek-ai/deepseek-v4.1-flash-1017`. On 2026-11-15 the first real Eval run showed that the endpoint answers `Model not found` for the `workers-ai/@cf/...` name.
  - `reasoningEffort`: `none`, `low`, `medium`, or `high`, sent as `reasoning_effort`. `none` turns thinking off on DeepSeek V4.1 Flash and cut the output tokens of a short reply from 76 to 8 in a live test. Use `none` for short chat replies. Use `low` or higher for the tasks that plan, call tools, or recall, and set the level from Eval results.
  - `tasks`: for each Model Task, `primary`, `secondary`, or `reviewer`. The repository value sends `reply`, `scheduled_task`, and `proactive` to `primary` (thinking `none`), and `eval_judge` to `secondary` (thinking `low`), with the same model. Only `pnpm control eval` uses `eval_judge`, to judge replies against a rubric. `auto_review` goes to `reviewer`, which for now has the model and the thinking of a reply (`none`), until a stronger reviewer model is chosen (decision [0039](../decisions/0039-auto-review.md)). A failed review asks the Owner.

  Every Model Task must have a row. A missing row is a type error in `test/model-gateway.test.ts`, which assigns the `MODEL_ROUTES` type that `wrangler types` generates to the route table type. A Turn that reads a table with a missing row, an unknown route name, or an empty model fails and names `MODEL_ROUTES`; it never uses a default route. To change a model, edit `MODEL_ROUTES` in `wrangler.jsonc`, run `pnpm --filter @repo/agent types`, and deploy. A deploy with `--var` sets only text values, so change the table in `wrangler.jsonc`.

- `MODEL_BILLING`: the billing mode of the Model Credentials, `unified-billing` (default) or `byok`. With `byok`, each request sends `cf-aig-no-wholesale: true`, so AI Gateway uses the Operator's stored provider key and does not fall back to Unified Billing. The setup of the stored key comes with `create-billy`.

The Model Gateway uses the AI Gateway REST endpoint, not the `/compat` endpoint, because Cloudflare marks `/compat` as deprecated for single-model chat completions. On this endpoint the token is a Cloudflare API token with the Workers AI Read permission, sent as `Authorization: Bearer`. Model Credentials are the token and the billing mode. Each request sends the Owner Id in `cf-aig-metadata` and `cf-aig-collect-log-payload: false`, so the gateway logs keep metadata and no prompt or reply text.

## Secrets

`wrangler.jsonc` lists the required Worker secrets in `secrets.required`. This list is the only source of secret names.

- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_WEBHOOK_SECRET`
- `AI_GATEWAY_TOKEN`: the Cloudflare API token for AI Gateway (Workers AI Read).
- `OPERATOR_TOKEN`: the bearer token of the Operator route.
- `MCP_SEALING_KEYS`: the keys that seal the MCP OAuth tokens at rest, one or more `<key id>:<base64 of 32 random bytes>` separated by commas. Create one with `openssl rand -base64 32`, for example `key-1:<output>`, and set it with `wrangler secret put MCP_SEALING_KEYS`. The first key seals new records and every listed key opens records. To rotate, put a new key first and keep the old key listed until the Owners have connected again. A key id has 1 to 32 letters, digits, `_`, or `-`. A lost key makes the sealed tokens unreadable, and the Owner must connect again.

For local dev, put them in `apps/agent/.dev.vars`. Git ignores this file. Never commit, log, or paste secret values. Deploying and setting secrets on Cloudflare need the repository owner's approval (decision 0037).

## Set up MCP Connections

The MCP Catalog has the Notion entry. A Notion connection needs no app registration at Notion, because the Edge serves a client metadata document. Do these steps one time for an Instance. Deploying and setting secrets need the repository owner's approval (decision 0037). Run the commands in `apps/agent`.

1. **Sealing key.** Create a key with `openssl rand -base64 32`. Store the secret `MCP_SEALING_KEYS` with the value `key-1:<output>`: run `pnpm exec wrangler secret put MCP_SEALING_KEYS` and paste the value at the prompt. A new Worker gets it in the `--secrets-file` of its first deploy. Keep a private copy: a lost key makes every Owner connect again. Do this before the deploy, because the secret is required.
2. **Edge origin.** Deploy with the public origin of the Edge: `pnpm exec wrangler deploy --var AI_GATEWAY_URL:<AI Gateway URL> --var EDGE_PUBLIC_URL:https://<Edge domain>`. A deploy sets the variables from `wrangler.jsonc` and `--var`, so pass both on every deploy. The deploy also creates the `McpHub` Durable Object class.
3. **BotFather.** In Telegram, send `/setdomain` to `@BotFather`, choose the bot of the Instance, and send the Edge domain (the host only, the same as in `EDGE_PUBLIC_URL`). BotFather accepts a `workers.dev` domain. Without this step Telegram refuses the Connect button.
4. **Button presses.** The Telegram webhook must receive `callback_query` updates (`allowed_updates` is `["message", "callback_query"]`), for Approve, Reject, and Details.
5. **Check.** Write "connect Notion" to the bot. A "Connect Notion" button comes. The button opens the consent page of the Edge, and after the sign-in at Notion the bot writes "Connected Notion (account <workspace name>)". The part in parentheses is absent when Notion sends no workspace name.

Before you remove the Notion entry from the Catalog, also by a revert of the code, ask each Owner who connected it to disconnect it. The agent cannot disconnect a Connection of an entry that the Catalog does not hold (decision [0036](../decisions/0036-mcp-connections.md)).

## Bundle size and startup

Measured on 2026-11-14 with `pnpm control bundle` (wrangler 4.162.0, Agents SDK 0.33.0, Effect 4.1.4, AI SDK 7.0.172, Drizzle ORM 1.0.0-rc.5). The Worker now includes the AI SDK, the OpenAI-compatible provider, and Effect Schema, so the full stack probe of the foundation slice is removed.

| Entry | Size (uncompressed) | gzip (not limited) | Local startup CPU |
| --- | --- | --- | --- |
| Worker (`src/index.ts`) | 4,215.65 KiB | 801.60 KiB | 319.7 ms |

Limits from the [Workers limits page](https://developers.cloudflare.com/workers/platform/limits/), read on 2026-11-13:

- Worker size: 64 MiB uncompressed, on the Free and the Paid plan. There is no compressed size limit. The 3 MB figure in the [feasibility study](../research/2026-11-12-cloudflare-feasibility.md) is out of date.
- Startup: the global scope must parse and run within 1 second.
- CPU time: 10 ms for each HTTP request on the Free plan. Waiting for network I/O does not count.

Result: the Worker uses 6.4% of the size limit. It fits the free plan for bundle size. Workers Paid is the supported plan ([decision 0008](../decisions/0008-workers-paid-plan.md)), so the free-plan CPU limit is not a release gate.

Startup CPU is measured on the local machine, which has a different CPU from Cloudflare. The numbers changed between runs on a shared machine, so `bundle` shows them but does not enforce them. The CPU time for each webhook request and each alarm Turn needs the deployed Worker and is measured in the live slice.
