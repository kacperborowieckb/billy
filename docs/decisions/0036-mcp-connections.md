# 0036: MCP Connections

Status: accepted

Date: 2026-11-26

Ticket [#151](https://github.com/kacperborowieckb/billy/issues/151) of spec [#150](https://github.com/kacperborowieckb/billy/issues/150). The spec asked for the number 0027, which is taken. It applies [0033](0033-prompt-and-conversation-architecture.md) and [0034](0034-architecture-review-changes.md), and it builds on [0027](0027-actions-and-approval.md) and [0029](0029-untrusted-tool-results.md). It replaces the MCP paragraph of [0009](0009-agent-loop-and-client-boundaries.md) ("MCP tools come from `this.addMcpServer()` in the Personal Agent"), and it replaces the exception of `capture_note` in 0029. This record covers the read path (#151), Approval (#152), and Side Sessions (#153). The tickets #154 to #158 add connect, tokens, refresh, disconnect, and the Notion entry, and each adds its decisions to this record.

## Decision

- **An MCP Hub for each Owner.** The MCP Hub is a Durable Object that is separate from the Personal Agent, named by the Owner Id. It owns the Agents SDK `MCPClientManager`, installed on its own Lifecycle (`agents/lifecycle`). The Personal Agent calls it only through RPC and our own interface (`McpHubPort`). SDK types do not leave `src/mcp/mcp-hub.ts`, its connector `src/mcp/mcp-server-connector.ts`, and the adapter `src/mcp/sealed-oauth-provider.ts`.
- **Lazy connect.** The SDK restores every stored server on wake and has no switch for it. The hub uses a subclass of the manager that overrides the public method `restoreConnectionsFromStorage` with nothing. A wake connects nothing. The hub connects one server on the first call for it, and waits at most `mcpConnectTimeoutMillis`. A Telegram message, an alarm, and an Approval press never call the hub, because the Personal Agent calls it only inside `call_mcp_tool` and at the add of a Connection.
- **The MCP Catalog is code.** `src/mcp/mcp-catalog.ts` has the typed entries: id, name, description, server URL, and for each tool a Risk Class and, for a `read` tool, the field that holds the id of a result with an id shape. The shapes are a UUID, a hex string of a fixed length (16 to 64), and a number, so no shape can hold words. A test of the Catalog fails for any other shape. Production has no entry now. The test-only entry `test_server` exists only when the Worker variable `MCP_TEST_SERVER_URL` is not empty. The Operator route `POST /operator/mcp-connections` adds a Connection for an Owner, and the test setup and `pnpm control request --mcp` use it. The first real entry (Notion) comes with #158.
- **Tool catalog copy.** The Personal Agent keeps the tool list and the state of each MCP Connection in its SQLite (`mcp_connections` and `mcp_tools`, a versioned migration), read through an Effect `Schema`. The hub sends the copy after a connect. A Turn reads a snapshot of the copy when it builds its tools and never waits for the hub to search.
- **Approval (#152).** `call_mcp_tool` computes the Risk Class of each call from the catalog entry, raised (never lowered) by the server annotation `destructiveHint: true`. A tool that the catalog does not list is `approve`. A `blocked` tool never runs, and the model gets the reason of the gate. The class goes through the spec 1 gate with no MCP exception: `read` runs, `approve` always asks, and `change` runs in an `owner` Turn and asks after an MCP result in the same Turn. Code checks the arguments against the cached input schema (`@cfworker/json-schema`, which needs no code generation) before the gate. A call that fails this check, names an unknown tool, or targets a Connection that is not `ready` is classed `read` for the gate, so it never makes a Pending Approval, and the tool refuses it with a reason.
- **Summary templates.** A catalog tool has an optional `summary` template with `{field}` placeholders for scalar arguments (dotted paths allowed). Code fills it from the frozen arguments, with strings quoted, cut, and on one line. The line starts with the Connection name from the catalog. A tool with no template gets "<Connection name>: <tool title>" and at most two scalar argument values; the title comes from the tool name with only letters and digits kept, never from server text.
- **Details.** Every Approval row has Approve, Reject, and Details. A Details press goes to the Personal Agent through a new RPC (`showApprovalDetails`), not through the inbox, because it changes no state. It answers the press and sends the redacted frozen input as a `.txt` file through the new Channel method `sendDocument`, for every stored Pending Approval, in any state, because the spec says that Details works while the Pending Approval exists. It changes no state.
- **Exactly once.** A tool can declare an external effect. For such a tool, an Approve press commits the `approved` state first, then runs the call outside the transaction, then commits the result. If the Durable Object stops during the call, the recovery finds an `approved` row with no result and sets it to `unconfirmed`. The call is never run again. Local tools keep one transaction, where a rollback gives a clean retry.
- **Fixed tools.** `find_mcp_tools` (`read`) answers from the copy with no hub call. It returns up to 5 matches with their input schemas, or a short index when more tools match. Its text is server text, so it comes inside the Untrusted Content markers. The class comes from the catalog and can only be raised by an annotation.
- **Results.** The result comes inside the Untrusted Content markers, so the Turn becomes `untrusted` by 0029. Code cuts it at `mcpResultMaxCharacters` with a visible marker. A call that times out (`mcpCallTimeoutMillis`) or fails returns a status and a notice to the model. Each call writes one `McpToolCalled` Journal Entry with the Connection, the tool, the Risk Class, and the status, without arguments or result.
- **Stub.** The stored Conversation gets a code-written Stub: the Connection name, the tool name, and the count of results. It lists the ordered ids that match the id shape of the catalog entry. Text that does not match the shape is dropped, and the Stub holds no title and no text of a result. The names in the Stub come from the catalog.
- **Owner Context Block.** The block lists the names and the states of the Connections, and the catalog entries that are not connected, with text from the catalog only. A state change replaces the block one time. The system text and the tool definitions do not change with the Connections.
- **Outbound refusal.** Every request of the hub goes through a guard that refuses non-HTTPS addresses, private, internal, loopback, and link-local addresses, names without a dot, and redirects. The Operator can name one exact origin as an exception for the test server (`MCP_TEST_SERVER_URL`).
- **Side Sessions (#153).** A Scheduled Task Turn and a Proactive Turn (the Brief and a Follow-up) get `find_mcp_tools` and `call_mcp_tool` in their fixed tool sets. `call_mcp_tool` there accepts only calls of the class `read`. A call of any other class (`change`, `approve`, `blocked`, an unlisted tool, or a `destructiveHint` raise) is `blocked` for the gate, so it never runs, the model gets the reason of the gate, and no Pending Approval exists (a Side Session cannot ask the Owner). Every MCP result is Untrusted Content, so after one the Side Session is `untrusted` by the rule of 0034: `close_open_loop` is denied and `set_schedule` stores the fixed prompt that code writes. A Connection that is not `ready` returns its state to the model as a tool failure, and the Turn continues and sends its message. The Write-back of a run that read a Connection holds a Stub in place of the sent text and names the Connection in its `read:` line, with the display name from the catalog and no text from the server. The Owner message Turn that answers it is `untrusted` through the existing rule of the connected Proactive Message. The reconnect button in the message of a Scheduled Turn is built in #156 (see "Token refresh and needs sign-in").
- **`capture_note` in an untrusted Turn (replaces the exception in 0029).** A new Note that links to no existing Note runs with no Approval in every `untrusted` Turn, and code marks the Note `untrusted`, whether the Burst or a tool result made the Turn `untrusted`. The gate has a new decision, `RunMarkedUntrusted`, and the tool gets it in its call. An edit or a link to an existing Note still needs Approval.
- **Connect from the chat (#154).** The tool `connect_mcp_server` (`read`, Owner message Turns only) checks the catalog id, refuses a Connection that is `ready`, and stores a connect request for the Turn. It changes nothing else. After the reply of the Turn is confirmed, code sends the Connect button as its own message through the new Channel capability "Owner proof link" (`sendOwnerProofLink`). The model never writes a link. The Telegram Channel implements the capability with a `login_url` inline button whose URL is `EDGE_PUBLIC_URL` plus `/mcp/connect?c=<catalog id>`. If the button cannot be sent, code sends a plain text that asks the Owner to try again.
- **Owner proof at the Edge.** `GET /mcp/connect` and `POST /mcp/connect` check the Telegram login data: the HMAC-SHA256 signature with the key SHA-256(bot token) over all fields except `hash` and `c`, an `auth_date` not older than 10 minutes (and not in the future by more than a minute), and a Telegram user id that is the Channel Identity of an active Owner in the Directory. The button URL also holds the routing id of the intended Owner's hub (`r`), and the Edge refuses a login whose Owner has another routing id, so a button that the Owner forwards to another registered Owner starts nothing. Any failure gives one error page for every cause and starts nothing, and the hub is not called. The consent page repeats the login fields in its form, so the POST proves the Owner again with no cookie. The hub uses up the login `hash` at the first POST that passes discovery (kept for 15 minutes), so a replay of the same login starts nothing. Known limit: a person who gets the Owner's already signed URL and posts it before the Owner does can start OAuth for the Owner's hub, and the tokens go to the Owner's hub only after that person signs in at the provider with their own account. The limit comes with the `login_url` model (a signed URL is the proof); the window is 10 minutes.
- **GET shows, POST starts.** The GET asks the hub only to describe the consent (server name from the catalog, the origin of the authorization endpoint, and the client mode), so Telegram link previews and crawlers start nothing and use up nothing. The POST asks the hub to start OAuth and answers 303 to the authorization URL. The pages are `no-store`, have no referrer, and cannot be framed.
- **Hub discovery and PKCE.** The hub finds the authorization server from the protected resource metadata of the catalog server URL (RFC 9728, with the server origin as the fallback) and the authorization server metadata (RFC 8414, then OpenID configuration). It requires PKCE S256 and a public HTTPS authorization endpoint (same guard as every hub request, which also refuses redirects). The client mode is CIMD when the server supports client ID metadata documents and the Edge origin is HTTPS (the client id is `/oauth/client-metadata.json` of the Edge, which exists on HTTPS only), else DCR with a public client (`token_endpoint_auth_method: none`), else the start fails. The request has `response_type=code`, the client id, the redirect URI `/oauth/callback` of the Edge, the S256 challenge, `resource`, and `state`.
- **State and nonce.** The state is `<hub routing id>.<nonce>`. The routing id is the Durable Object id string of the Owner's hub. It is opaque, it is not the Owner Id or a Channel Identity, and the Edge can find the hub from it with `idFromString` (the callback ticket uses this). The nonce is 32 random bytes, base64url. The hub keeps the pending request (catalog id, code verifier, client id, redirect URI, issuer, expiry of 10 minutes) under `oauth:<nonce>` in its storage and deletes expired ones at each start. The callback (#155) checks and uses up the nonce. The Connection state becomes `authenticating` at the start. The code verifier is sealed (see "Sealed token store").
- **OAuth callback (#155).** `GET /oauth/callback` on the Edge reads `state`, `code`, `iss`, and `error`. It finds the hub with `idFromString` of the routing id (a 64-character hex string; any other shape, or an id of another namespace, gives the same error page) and calls `completeOAuth`. The Edge does not exchange the code; it only passes it to the hub. The hub keeps the pending request under `oauth:<nonce>` with the Owner Id (the hub that the callback finds has no name, so the pending record carries it). The hub checks, in this order: the nonce exists and has not expired, the `iss` agrees, and the callback has a `code` or an `error`. A failure of any of these changes nothing, and the pending request stays, so a forged callback cannot use up the Owner's request. A good callback deletes the pending request first (the nonce is single use), then exchanges the code. A callback with `error` sets the state `failed`. A failed exchange sets the state `failed`, and the Owner must ask Billy to connect again.
- **`iss` (RFC 9207).** The hub stores whether the authorization server metadata has `authorization_response_iss_parameter_supported: true`. When the callback has an `iss`, it must equal the issuer of the metadata. When it has none, the callback is accepted only if the server did not promise one.
- **Token exchange.** The hub sends `grant_type=authorization_code`, the code, the redirect URI, the client id, the code verifier, and `resource` (RFC 8707) to the token endpoint of the metadata. The registration asks for a public client (`token_endpoint_auth_method: none`). If a DCR server returns a client secret anyway, the hub seals it (with the nonce as part of the associated data until the exchange, then in the sealed client record) and sends it in the way that the registration response names (`client_secret_basic`, the default of RFC 7591, as an `Authorization: Basic` header, or `client_secret_post` in the request body; any other method fails the start before the Owner is redirected) in the token request and with later refreshes, so a server that issues a secret still completes the exchange. The token type must be Bearer. Discovery refuses a token endpoint or a registration endpoint that is not a public HTTPS address, like the authorization endpoint. Every request of the hub to an OAuth endpoint, the body read included, has a deadline of 3 seconds.
- **Completions of one entry run one at a time.** A queue for each catalog entry runs the check of the recorded Connection, the code exchange, the credential write, and the connect of one completion before the next completion starts, so two callbacks cannot overlap and leave credentials of one account under the live Connection of another.
- **A start runs its last step in the same queue.** The start does its network work (discovery, registration) outside the queue, then runs inside the queue of the catalog entry: it checks the recorded Connection again, stores the pending request, and sets the state `authenticating`. A start that finds a recorded Connection stores nothing, changes no state, and shows the already-connected page. So a start that paused during a callback cannot set `authenticating` over a `ready` Connection. A start that ran first leaves its pending request, and a later callback of it is refused as already connected with the state still `ready`; an abandoned start only leaves a pending request that expires.
- **Two authorizations for one Connection.** The tokens are stored for each catalog entry, not for each attempt, and `latest-exchange:<catalog id>` names the nonce of the last exchange. A completion for an entry that already has a recorded Connection is refused before the code exchange (the page says it is already connected), so the live Connection, its account label, and the stored tokens always describe one account. A replay of an earlier attempt is refused when a later attempt replaced the tokens (its nonce is not the latest exchange). A replay of the latest attempt always calls the connect step again, even when the Connection record exists, because the hub writes the record before the Personal Agent call and a stop between the two would leave the Personal Agent without the completion; the Personal Agent ignores a completion that it already has.
- **Replay.** The hub writes `settled:<nonce>` (the Owner Id, the catalog id, the issuer rule, the account label, 15 minutes; a replay must pass the same `iss` check) in the same storage write as the sealed tokens and `latest-exchange`, so the three exist together or not at all. A second callback with the same state finds no pending request and finds the marker. If the Connection is recorded, it shows the same success page. If the first connect failed or the Durable Object restarted before it finished, the replay connects with the saved tokens and finishes the Connection, with no new token request. The replay window of 15 minutes is a choice: the pending request itself lives 10 minutes. It makes no token request, no second Connection, and no second message. Two callbacks that arrive together share one run.
- **Sealed token store.** The hub does not use the SDK key-value storage for secrets. A `SealedOAuthProvider` (the SDK hook, `transport.authProvider`) reads and writes the tokens and the client information under `tokens:<catalog id>` and `client:<catalog id>`. The records are sealed with AES-256-GCM, a new random 96-bit nonce for each record, and the key id in the record (`v1.<key id>.<nonce>.<ciphertext>`). The associated data is the Owner Id, the catalog id, and the purpose, so a record that is copied to another Connection or Owner does not open (the pending code verifier also binds its nonce). The key is the Worker secret `MCP_SEALING_KEYS`: a list `<key id>:<base64 of 32 bytes>` separated by commas. The first key seals; every key opens, so a rotation adds a new first key and keeps the old one until the records are sealed again. A missing or invalid secret makes a connect fail with a logged error that names no value. A save of tokens keeps the old refresh token when the new response has none. The refresh, `invalid_grant`, and `needs sign-in` are in "Token refresh and needs sign-in" (#156).
- **After the exchange.** The hub connects to the server with the new token, lists the tools, and calls `receiveMcpConnected` on the Personal Agent. That call stores the tool copy, sets the state `ready`, writes an `McpConnectionAdded` Journal Entry (the Connection only, no secret), and sends "Connected <name> (account <label>)" to the Owner Channel Conversation. The account label comes from the token response field `account_name`, else `workspace_name`; control characters are removed and it is cut at 80 characters, because it is text from the server. With neither field the message is "Connected <name>". Whether the real Notion token response has one of these fields is checked with #158. The Personal Agent gets the nonce as the completion id. It writes the Journal Entry with the event id `mcp-connection-added:<completion id>` first and sends the message after it, and a completion that it already knows only sets the state `ready` (the hub has just connected, inside the queue of the entry, and the completion is the latest exchange) and writes and sends nothing else, so a replay after a restart or after a lost result makes no second Journal Entry and no second message and the state matches the Connection of the hub (a message that was lost between the two steps is not sent again). The Personal Agent writes the check of the completion id, the tool copy, the state, and the Journal Entry in one transaction, so two calls with the same completion id cannot both write; the message is sent after the transaction. The hub records the Connection before it calls the Personal Agent and removes the record if the call fails, so a success that the hub reports is never ahead of the Personal Agent state. A failed connect after the exchange sets the state `failed`; the sealed tokens stay and a new connect replaces them.
- **A replay keeps the first tool copy.** A completion that the Personal Agent already knows does not replace the tool copy. The hub sends the current tools with it and the Personal Agent drops that list, so a server that changed its tools between the first completion and the replay shows the older copy until the next refresh. The refresh (after `tools/list_changed` and on request) comes with a later ticket of #150. The choice keeps the replay free of writes, so it cannot replace a newer copy.
- **Known limit: names that resolve to private addresses.** The outbound guard checks the host text of a URL. A Worker cannot pin the address that `fetch` resolves, so a lookup before the request would not stop DNS rebinding, and the guard does not add one. We did not verify that the Workers runtime refuses a name that resolves to a private address (the Cloudflare documents say that a raw IP address is refused, and nothing in them settles the case of a name). Treat the guard as one layer. The MCP Catalog fixes the server URL, so only OAuth metadata can name another host, over HTTPS, and a request to such a host sends the code and the PKCE verifier, which are useless without the Owner's pending request. Revisit if the runtime is shown to route such requests.
- **Known limit.** A callback with a routing id of the right shape wakes a hub Durable Object even if no Owner has that id; the hub has no pending request and answers "not started". The Edge cannot tell more without a lookup of routing ids.
- **Token refresh and needs sign-in (#156): one state machine.** All changes of the hub state of one Connection run in the one queue of the entry (`KeyedQueue`): the OAuth start, the callback, the replay, the connect step, every token refresh, and the move to `needs sign-in`. The hub state is the record `connection:<catalog id>` (`ready` or `needs_sign_in`; the old value `true` reads as `ready`) and `last-error:<catalog id>`, both written by `McpConnectionLedger`. `McpConnectionHealth` is the only code that reads the tokens to refresh them or moves the state to `needs_sign_in`. The SDK never refreshes: `SealedOAuthProvider.tokens()` gives nothing, and every request of the MCP transport goes through `authorizedFetch`, which adds the sealed access token, so the SDK has no refresh token to use.
- **Refresh.** A request that finds the access token near its expiry (`expires_at_millis`, 60 seconds of margin), or that the server answers with 401, asks `McpConnectionHealth` for a token. Inside the queue the health code reads the tokens again. If the token that the caller used is no longer the stored one, a refresh or a reconnect already ran, and the caller gets the stored token with no token request (this is the single flight: two calls cause one request). Otherwise it sends one `refresh_token` request to the token endpoint that the callback stored in the sealed client record, with the same client authentication and `resource` as the code exchange. A response with no refresh token keeps the old one (`saveTokens`); a rotated one replaces it. A request is retried once with the new token. Every token request has a deadline (3 seconds) that covers the body read. A 400 or 401 with `invalid_grant`, `invalid_client`, or `unauthorized_client`, a missing refresh token, or a second 401 after a refresh moves the state to `needs_sign_in`. A 403 with `insufficient_scope` does the same, with no refresh and no background sign-in. Any other failure (network, deadline, 5xx, a body that is not a token response, a failed save) leaves the state `ready`, writes the last error `unavailable` or `failed`, and fails the call. A rotated refresh token that the provider accepted and that we lost (the response body did not arrive, or the save failed) ends the next refresh with `invalid_grant`, so the state becomes `needs_sign_in` and the Owner gets the reconnect button; nothing fails without a word. A failed move also never resurrects tokens: the move deletes the sealed tokens.
- **A connect under the queue does not refresh.** The callback and the replay connect while they hold the queue, and a refresh would wait for that queue forever. While the queue holder waits for a connect, the requests of the connect use the stored token and do not refresh. A 401 there fails the connect (the state becomes `failed`).
- **Interleavings.** A stale call that the server rejected with the old token, after a reconnect finished, finds new tokens in the queue and retries with them. A call that is already running keeps its token and finishes while another call refreshes. A reconnect (start or callback) that arrives during a refresh waits for it; a refresh that arrives during a callback waits for the callback. The start of a reconnect does not tell the Personal Agent `authenticating` when the hub state is `needs_sign_in`, so the state stays `needs_sign_in` until the callback decides. The Operator add and the explicit catalog refresh follow the same rules: the add runs in the queue and never replaces `needs_sign_in`, and the catalog refresh does not hold the queue while it talks to the server, so a request of it can refresh the token. A replay of a callback does nothing when the sealed tokens are gone. The tests force each order with a hold and a release.
- **Personal Agent.** The hub tells the Personal Agent `needs_sign_in` at the move and again when a call finds it. `McpConnectionStateChanged` (catalog id and new state) is written at every change of the stored state, in the transaction that changes it (also for `ready` after a reconnect). A call that finds a Connection that is not `ready` (the state in the Personal Agent, or `needs_sign_in` and `insufficient_scope` from the hub) is refused with a tool result that says the task is not done and that code adds a Reconnect button, and it stores a connect request for the Turn. The request is keyed by Turn and catalog id, so the Turn has the button once. The button is the Owner proof link of #154, labelled "Reconnect <name>" when the state is `needs_sign_in`. A Scheduled Task Turn and a Proactive Turn (the Brief) also store the request for every Connection in `needs_sign_in` when they start, so their message has the button even when the model reads nothing. The Delivery code sends the buttons after the message, as for a connect.
- **Last error.** The hub keeps one record for each Connection: the phase (`token_exchange`, `connect`, `refresh`, or `request`), a fixed reason, the HTTP status, and the time. It holds no text from a server and no token. The Operator reads it through the hub RPC `lastError`.
- **Disconnect (#157): a state of the same machine.** `disconnect_mcp_connection` (`change`, Owner message Turns only) asks the hub to disconnect, and the Personal Agent then removes its own record, tool copy, and connect requests, makes the open Pending Approvals of that Connection due at once, and writes `McpConnectionRemoved` (the Connection and the revocation result, no secret), in its own transaction, then drops the Connection from the tool snapshot of the Turn, so a later `find_mcp_tools` or `call_mcp_tool` of the same Turn answers "not connected". The hub does not call the Personal Agent for this, because a call back into the Personal Agent could wait for a Personal Agent transaction. For that reason a tool with an external effect now runs its work outside the transaction and records its result in a transaction after it (`recordingToolCall` with `runsOutsideTransaction`); before, a hub call that waited for the entry queue while a callback in the queue waited for the Personal Agent could not finish. The hub disconnect runs in the one queue of the entry, in this order: (1) read the sealed tokens and the client record; (2) delete in one write the tokens, the client record, the Connection record, the last error, `latest-exchange`, and every pending request and settled marker of the entry; (3) end the live connection (`McpServerConnector.forget`: it raises an epoch, drops a connect that is running, and closes the connection under the queue hold with a deadline of 3 seconds); (4) revoke at the provider. Local deletion comes before revocation so that tokens are deleted in every case, also when the revocation hangs or the Durable Object stops. The hub also writes a removal marker (`removing:<catalog id>`, 60 seconds) in step (2), and the tool calls the hub RPC `acknowledgeRemoval` after the Personal Agent removal. While the marker lives, an OAuth start answers "unavailable", so a reconnect cannot finish between the hub deletion and the Personal Agent removal, and the removal can never delete the copy of a newer Connection. The Operator add also fails while the marker lives. The tool catalog sync delivers a copy only when the Connection record is `ready`, checked inside the queue, and a catalog refresh that opened a connection while the Connection was removed closes it and answers `not_ready`. A disconnect that finds nothing is not an error and repeats the steps, so a retry after a stop between hub and Personal Agent finishes the Personal Agent side.
- **Revocation.** The authorization server metadata may name `revocation_endpoint`. Discovery keeps it only when it is a public HTTPS address (same guard) and stores it in the pending request and then in the sealed client record; a Connection from before #157 has none. The hub sends RFC 7009 requests for the refresh token and the access token, in parallel, with the client authentication of the token endpoint. Every request has the deadline of 3 seconds, the body read included. A status that is not 2xx, a network failure, and a deadline give `failed`; no endpoint or no token gives `not_attempted`. The result goes to the Journal and the model, and a failed revocation never stops the deletion. The tool result tells the model to say that the Owner can remove Billy in the settings of the service.
- **Interleavings of a disconnect.** (a) A callback that holds the queue finishes first, and the disconnect then removes the new Connection. (b) A callback that waited behind a disconnect finds that its pending request is gone: the callback now checks and deletes the pending request inside the queue, not before it, so it exchanges nothing. (c) A replay after a disconnect finds no `latest-exchange` and no settled marker and does nothing. (d) A refresh that holds the queue finishes first. A refresh or a recovery from a 401 that runs after a disconnect finds no Connection record: the health code answers "not connected" and never writes `needs_sign_in` for a removed Connection. (e) A call that is running loses its connection and fails; the gateway answers `not_connected` when the record is gone, and an approved call that was cut is `unconfirmed` by the existing rule. A connect that was running when the disconnect came is awaited (with a deadline) under the queue hold and closes itself at its end (epoch check), so it cannot close a later Connection. (f) A Pending Approval for `call_mcp_tool` of the Connection becomes due at the disconnect, so Approve shows "This expired" and runs nothing, also after a reconnect that gives the same catalog id another account. (g) A start that finishes its last step after the disconnect is a new connect and sets `authenticating`; the reconnect right after a disconnect works as a first connect. The tests force each order with a hold and a release.
- **Owner removal.** The hub RPC `removeOwnerStorage` ends the connections of every entry under their queues and deletes the whole hub storage. No flow removes an Owner yet (Forget, #138); that flow calls this RPC.
- **Catalog copy follows the server.** The hub listens to the manager's state events. After `tools/list_changed` the connection fetches the tools again, and the hub sends the new copy to the Personal Agent when it differs from the last copy that it sent. The RPC `refreshToolCatalog` does the same on request. Known limit: the SDK holds one standing GET stream for these notifications, and that stream has no deadline; every other MCP request has a deadline of 120 seconds (`mcpRequestDeadlineMillis`), which also covers a streamed body.
- **BotFather `/setdomain`: accepted.** On 2026-11-27 the repository owner ran `/setdomain` for the bot with the deployed `workers.dev` Edge domain, and BotFather accepted it. The `login_url` path is the one built. The fallback (one-time link with a 10 minute life, preview off) is not built and stays a "Revisit if" item for a domain that BotFather rejects. The Operator setup docs add the manual `/setdomain` step and the Worker variable `EDGE_PUBLIC_URL`.

## Why

The spec of #150 says that the gate rules apply with no MCP exceptions and that a new Note saves with no Approval after an MCP result. 0029 required Approval for it, because the Note would be an `owner` Note with text that can copy Untrusted Content. Marking the Note `untrusted` removes that risk, and the Owner keeps "read my page and keep the main points" as one message.
